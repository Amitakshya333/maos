# Phase F10-09 Verification: CLI / GUI Equivalence Fixtures

## 1. Overview & Requirements
- **Goal:** Validate that the CLI and GUI are pure adapters over identical application services, sharing exact DAG, tool, provenance, sandbox, approval, interruption, and output semantics.
- **Specification:**
  - Scope: same service operations for task/DAG/approval/artifact/stop.
  - Acceptance: equivalent typed records/hashes across CLI and GUI.
  - Negative Requirements:
    1. Zero GUI shell-out: GUI never invokes CLI commands or shells out via `child_process`, `execSync`, `spawn`, etc.
    2. Zero client-specific semantic divergence: Neither adapter contains diverging business logic, state machines, or fake completion states.
    3. Mandatory confirmation defense: Force-stop mandates explicit confirmation flag/parameter across both adapters.

## 2. Implementation Summary

### A. Equivalence Fixture Contract (`fixtures/f10-09/cli-gui-equivalence-contract.json`)
Defined authoritative mapping for all 5 core operations:
1. **Task Execution:** CLI `executeJudgedRun` vs GUI `POST /api/v1/tasks/:id/execute` -> `TaskService`.
2. **Workflow DAG & Projections:** CLI `projectWorkflowState` vs GUI `GET /api/v1/cockpit/:runId/projection` -> `CockpitService` / `projectWorkflowState`.
3. **Approval Governance:** CLI `ApprovalService.decideApproval` vs GUI `POST /api/v1/approvals/:id/decide` / `review` -> `ApprovalService`.
4. **Artifact Management:** CLI `ArtifactService.finalizeArtifact` vs GUI `POST /api/v1/artifacts` & `GET /api/v1/artifacts/:id` -> `ArtifactService`.
5. **Lifecycle Stop & Interruption:** CLI `runIndustrialStop` vs GUI `POST /api/v1/cockpit/stop` -> `CockpitService.executeRunStop` / `ProjectService.stopService`.

### B. Static Audit: Zero GUI Shell-Out
- Scanned all TypeScript/TSX source files under `src/gui/src/`.
- Verified zero instances of `child_process`, `execSync`, `execFile`, or `spawn`.
- Confirmed that the React Cockpit GUI operates strictly in-browser and communicates exclusively via typed HTTP REST (`MaosRestClient`) and WebSocket event subscriptions.

### C. Equivalence Validations Across Operations
1. **Workflow & DAG Projection Equivalence:**
   - Both CLI application service projection and REST endpoint `/api/v1/cockpit/:runId/projection` produce identical `WorkflowRunProjection` objects with identical stages (`INGEST_DATA`, `ANALYZE_TELEMETRY`), statuses, task counts, routes, and timings.
2. **Approval Governance Equivalence:**
   - Evaluated decisions submitted via direct service (`ApprovalService.decideApproval`) and via REST API (`POST /api/v1/approvals/:id/review`).
   - Confirmed identical `ApprovalRecord` schema, identical resolution fields (`status: 'approved'`, `approvedBy`, `reviewedBy`, `reviewRole: 'lead'`), and identical audit logging.
   - Tested unauthorized reviewer role rejection (`UNAUTHORIZED_REVIEWER_ROLE`): both fail closed and reject decisions from non-human or untrusted roles.
3. **Artifact Integrity & SHA-256 Equivalence:**
   - Verified that artifact deliverables finalized via direct service and queried via REST API have byte-for-byte identical authoritative SHA-256 hashes.
   - Verified that path traversal (`../../outside.docx`) is rejected with `PATH_TRAVERSAL` across both interfaces.
4. **Lifecycle Stop & Confirmation Defense:**
   - Verified that unconfirmed force-stop fails closed across both CLI (`CONFIRMATION_REQUIRED`, exit code 4) and REST (`FORCE_STOP_CONFIRMATION_REQUIRED`, HTTP 400).
   - Confirmed graceful stop (`mode: after-current-tasks`) transitions status to `stopped` identically across both interfaces.
