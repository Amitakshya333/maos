## Executive Summary

Task **UI1-14** delivers the authoritative Approval system and GUI workflows for critical operations across MAOS. All approval decisions, validations, and state transitions are backed directly by persistent backend services (`ApprovalService`, `FairQueueService`, `TaskService`, and `AuditService`), completely eliminating ephemeral or GUI-only approval state.

### 1. 8 Mandatory Approval Scopes
1. `docx_generation` — Required for generating Word document artifacts.
2. `xlsx_generation` — Required for generating Excel spreadsheet artifacts.
3. `pptx_generation` — Required for generating PowerPoint presentation artifacts.
4. `safety_verdict` — Required for applying automated or manual safety decisions.
5. `artifact_overwrite` — Required for overwriting existing stored artifacts (`UNAUTHORIZED_OVERWRITE`).
6. `force_stop` — Required for terminating executing tasks and canceling queued work (`FORCE_STOP_CONFIRMATION_REQUIRED`).
7. `reviewer_signoff` — Required for final human sign-off on workflow completion.
8. `project_scoped_write` — Explicitly allowed project-scoped filesystem mutations governed by policy.

### 2. Strict 15-Field Approval Record Preservation
Every `ApprovalRecord` persistently preserves all 15 required fields on disk (`.maos/approvals/`):
- `approvalId`: UUIDv4 identifier
- `projectId`: Scoped project root
- `runId`: Specific workflow execution run
- `taskId`: Associated task identifier
- `stepId`: Workflow step identifier
- `actorId`: Identity of the requestor or approving authority
- `actorRole`: Authorized role (`reviewer`, `lead`, `admin`, `operator`, `user`, `auditor`, `sec-officer`, `engineer`, `compliance-officer`)
- `status`: One of 5 authoritative states: `pending`, `approved`, `rejected`, `revoked`, `expired`
- `reason`: Required rationale for request or review decision
- `scope`: One of the 8 authoritative approval scopes
- `createdAt`: ISO 8601 creation timestamp
- `expiresAt`: ISO 8601 expiry timestamp (dynamic or static TTL evaluation)
- `payloadHash`: SHA-256 of the exact payload content
- `sourceHashes`: Array of SHA-256 hashes of input source materials
- `artifactIds`: Target artifact identifiers governed by the approval

### 3. Fail-Closed Validation & Security Invariants
- **Non-Reusable Scope (`OPERATION_REUSE_REJECTED`)**: An approval granted for one payload, artifact, run, or task cannot be reused for another. After execution, an approval is consumed via `consumeApproval` and marked `revoked`. Attempting to consume or reuse an already consumed approval fails closed.
- **Dynamic & Static Expiration (`APPROVAL_EXPIRED`)**: Approvals older than their TTL (`expiresAt`) are rejected both statically and dynamically upon access. Expired records are transitioned to status `'expired'` on disk.
- **Payload & Source Hash Binding (`PAYLOAD_HASH_MISMATCH`, `SOURCE_HASH_MISMATCH`)**: Any modification to downstream payloads or source artifacts invalidates the approval.
- **Cross-Boundary Protection (`CROSS_PROJECT_APPROVAL_USE`, `CROSS_RUN_APPROVAL_USE`)**: Approvals are bound to their originating `projectId` and `runId`. Re-using an approval across projects or runs is rejected.
- **Anti-Auto-Approval Defense (`AUTO_APPROVAL_FORBIDDEN`)**: Creation requests cannot specify status `'approved'` or `'rejected'`. All approvals must enter via `'pending'`.
- **Untrusted Model Prose Defense (`UNTRUSTED_SELF_APPROVAL_REJECTED`)**: Autonomous LLM/agent models cannot approve their own requests. Approving actors starting with `agent_`, `model_`, `assistant_`, `bot_`, or `system_` are strictly rejected.
- **Authorized Human Role Enforcement (`UNAUTHORIZED_REVIEWER_ROLE`)**: Only authorized human roles can decide approvals.
- **Rejection Justification**: Rejection decisions mandate a non-empty `notes` field explaining the rationale.
- **Zero Prompting for Read-Only Operations**: Read-only operations (ordinary text/code inference, similarity queries, sandboxed execution) are verified via `isReadOnlyOperation` and proceed unprompted without approval barriers.

### 4. Force-Stop Operation & Phantom Success Prevention
- Force-stop operations mandate explicit human confirmation (`confirmed: true`); unconfirmed calls are rejected with `FORCE_STOP_CONFIRMATION_REQUIRED`.
- When confirmed, `ApprovalService.executeForceStop`:
  - Halts the active task via `TaskService.interruptTask`, transitioning it to status `'interrupted'`.
  - Cancels any pending queue entry via `FairQueueService.cancelEntry`.
  - Emits an append-only audit event recording the interruption.
  - Prevents downstream workers from reporting success or creating trusted artifacts after a force-stop (`PHANTOM_SUCCESS_REJECTED`).

### 5. Interactive GUI Views & 4-Way Client Parity
- **Approvals Cockpit (`src/gui/src/views/ApprovalsView.tsx`)**:
  - Scope and status tab filters for navigating pending, approved, rejected, and expired requests.
  - Cards displaying all 15 fields, actor identities, relative time-to-expiry badges, and cryptographic hash chips.
  - Review Modal supporting authorized human reviewer role selection, conditional notes, and rejection rationale.
  - Force-Stop Modal with explicit danger confirmation checkbox and interruption warnings.
- **4-Way Client Parity**:
  - Direct TypeScript service container (`ServiceContainer.approvals`)
  - REST API Router (`/api/v1/approvals*`) with standard status code mappings (200, 201, 400, 403, 404, 409)
  - Backend Client (`MaosRestClient` in `src/api/client.ts`)
  - Frontend REST Client (`BrowserRestClient` in `src/gui/src/api/rest-client.ts`) with runtime validation (`validateApprovalRecord`, `validateApprovalsList`, `validateApprovalCheckResult`, `validateForceStopResult`)
  - UI State Adapter (`GuiApiAdapter` in `src/gui/src/api/adapter.ts`)
