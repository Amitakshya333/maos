## 3. Verified Security & Resilience Invariants

### 1. Loopback Binding, Origin Validation & Anonymous Rejection
- **DNS Rebinding Defense:** Validates `Host` header against local loopback interfaces (`127.0.0.1`, `localhost`, `[::1]`). Requests using arbitrary domain names (e.g., `attacker.evil.com`) are rejected with `403 DNS_REBINDING_DETECTED`.
- **Origin Validation:** Cross-origin web requests from untrusted web pages are rejected with `403 INVALID_ORIGIN`. Only the local desktop client origin is accepted.
- **Session Authentication:** Unauthenticated requests lacking a valid Bearer token are blocked with `401 UNAUTHORIZED`.

### 2. Run Interruption, Reattach, Event Stream Loss & Replay
- **Cockpit State Reconstitution:** Upon connection loss or UI reload, the frontend queries the Cockpit API and reconstructs the run state without re-executing completed operations.
- **Cursor Resumption:** Event stream replay resumes from the client's last acknowledged cursor (`lastCursor`), ensuring zero event loss and zero duplicate event dispatch.
- **Monotonic Sequence:** Events received during replay strictly follow monotonically increasing step sequence IDs.

### 3. Atomic Artifact Finalization & Interruption Rollback
- **Two-Phase Commit / Temp Staging:** Artifacts are written to `.maos/temp/artifacts/...` before atomic rename into the final project workspace.
- **Clean Write Rollback:** If an interruption occurs during write or stream closing, incomplete and corrupted destination files are never created.
- **Orphan Cleanup:** Staged temporary files left behind by ungraceful service terminations are cleaned up by `cleanupOrphanTempFiles()`.

### 4. Force-Stop & Phantom Success Defense
- **Explicit Confirmation Requirement:** Destructive termination requires explicit confirmation (`confirmed: true`); unconfirmed calls are rejected with `FORCE_STOP_CONFIRMATION_REQUIRED`.
- **Phantom Success Defense:** Once force-stopped, a run is immediately transitioned to `INTERRUPTED` / `STOPPED` and can **never** transition to `COMPLETED` or emit false positive deliverables.

### 5. Stale & Cross-Run Approval Rejection
- **Non-Existent Approvals:** Handled with explicit `404 NOT_FOUND` rather than unhandled server errors.
- **Cross-Project Scope Rejection:** Approvals belonging to foreign projects cannot be reviewed or modified.
- **Single-Use Transitions:** Already decided approvals cannot be re-approved or overridden, rejecting reuse attempts with `400` / `409`.
