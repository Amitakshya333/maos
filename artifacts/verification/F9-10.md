## Problem being resolved

Three product-level blockers made the Industrial sovereignty gate unreachable,
independent of any host firewall configuration:

1. **No production caller could apply the boundary.** `FirewallService.applyPlan`
   and `synthesizePlan` had zero callers outside tests; no CLI command, API route,
   or GUI control reached them. `Boundary Status: BLOCKED` was therefore
   permanent by construction, not a misconfiguration.
2. **No production caller started the network monitor.** `NetworkMonitorService.startObservation`
   had zero callers in `src/`. `monitorActive` was structurally always `false`,
   so the gate could not pass even with an active firewall.
3. **The enforcement path was ambiguous and unsafe.** The synthesized host plan
   blocked all inbound and outbound traffic on all addresses and profiles with no
   program scoping — disabling the workstation's networking wholesale, while not
   restricting loopback traffic, which is where the boundary matters.

F9-10 resolves all three by deciding the boundary's scope and implementing the
lifecycle at that scope.

---

## Scope decision

**The Industrial boundary is process-scoped.** The claim is *"the MAOS process
tree communicated only over declared loopback endpoints during this run, and no
host firewall state was modified"* — not *"this workstation was isolated."*

Full rationale, alternatives considered, and stated limitations:
[docs/BOUNDARY_SCOPE.md](../../docs/BOUNDARY_SCOPE.md).

## Verified properties

### 1. No host mutation (the safety property)

`ProcessBoundaryService` never constructs a platform firewall adapter. The test
suite wires a `HostMutationDetector` adapter that records every host-mutating
invocation, runs the full lifecycle (`enable` → `getStatus` → `verifyEnabledBoundary`
→ `disable`) plus `selfTest`, and asserts:

- `detector.calls` is empty — zero host adapter invocations
- `detector.getInstalledRuleCount()` is 0
- `.maos/firewall/active-plan.json` is never created
- `hostFirewallModified === false` and `elevationRequired === false` at every stage

### 2. The gate is reachable

With the boundary enabled, `getIndustrialBoundaryStatus` returns
`overallStatus: VERIFIED`, `firewallStatus: ACTIVE`, `monitorStatus: CAPTURING`,
`boundaryScope: process`. All five `assert*Allowed` execution assertions resolve.
`maos industrial preflight` returns `SUCCESS` when diagnostics pass.

### 3. `ACTIVE` is measured, never inferred

- A record whose observation session has ended reports `INACTIVE` — never `ACTIVE`.
- A policy re-sealed under an enabled boundary reports `RESTORE_REQUIRED`.
- `verifyEnabledBoundary` re-derives the expected plan from the sealed policy and
  compares canonical hashes. A record with every constraint ID intact but a
  mutated constraint *value* is detected as invalid — the exact failure a
  name-only verifier would miss.

### 4. Attribution scope is enforced and reported

Non-loopback traffic from a PID outside the attributed tree (simulated browser
traffic) neither blocks nor blesses the boundary. Non-loopback traffic from an
attributed PID blocks it. The resolved scope is recorded in the plan and printed
in status detail, including a `attributionComplete: false` marker when process
tree resolution degrades to the root process only.

### 5. Fail-closed behaviour

| Condition | Result |
| --- | --- |
| `enable` without `confirm` | `FIREWALL_CONFIRMATION_REQUIRED`; no session, no record, no host call |
| `disable` without `confirm` | `FIREWALL_CONFIRMATION_REQUIRED`; boundary untouched |
| Non-loopback declared endpoint | Synthesis refused: *"not loopback-only"* |
| `disallowDnsResolution: false` | Synthesis refused: *"permits DNS resolution"* |
| `enforceLoopbackStrict: false` | Synthesis refused: *"strict loopback"* |
| Tampered policy hash | Synthesis refused: *"policy hash mismatch"* |
| Process scope without a boundary service | Construction refused: *"Refusing to silently fall back"* |
| Plan claiming `hostFirewallModified: true` | Validation refused |
| Attributed non-loopback connection | `PREFLIGHT_BLOCKED`, self-test `verified: false` |

### 6. Teardown is a real restore

`disable` stops the live session, persists the observation trace to
`.maos/network-evidence/<sessionId>.json`, and clears the record. It is
idempotent on an absent boundary, and re-enabling an identical boundary reuses the
existing session rather than churning it. A widened scope supersedes and tears
down the previous session.

## Integration points

| Surface | Change |
| --- | --- |
| `createServiceContainer` | Explicitly selects `boundaryScope: 'process'`; exposes `processBoundary` |
| `maos industrial preflight` | Establishes the boundary, evaluates the real gate against it, measures, then tears down; reports scope, host-firewall neutrality, attribution, and failures with actionable diagnosis |
| `maos industrial boundary enable\|status\|disable` | **New.** The lifecycle surface that previously did not exist |
| `maos industrial run --enforce-firewall` | Establishes the boundary for the run's duration, executes inside it, halts with `PREFLIGHT_BLOCKED` if it cannot be established, and tears down persisting evidence |
| `ProcessBoundaryService` | Exit hook ties record lifetime to the holding process, so short-lived holders leave no stale record. One shared `process.on('exit')` listener serves all instances |
| `NetworkMonitorService` | Metadata resolution restricted to the attribution scope; live observation summary now exposes violation descriptions |
| `AtomicCleanupCoordinator` | Teardown clears boundary records via `processBoundariesDisabledCount` |

### Preflight ordering

Preflight establishes the boundary **before** reading the gate, and tears it down
after. An earlier iteration read the gate after a self-test had already torn the
boundary down, so it correctly reported `INACTIVE` and blocked — a real bug found
by running the CLI on Windows, not by the unit suite. The current sequence is:

```
enable → read gate status → self-test measurement → disable
```

### Cost of measurement (found by the test suite)

Host socket observation is a PowerShell round trip (~1.1 s per enumeration on the
target host, plus ~0.6 s for the process tree). Three things followed from
measuring rather than assuming:

1. **Metadata resolution was unbounded.** The monitor resolved process metadata for
   *every* socket on the host before evaluating — hundreds of subprocesses per
   sample, for sockets outside the attribution scope that are never evaluated.
   Resolution is now restricted to in-scope sockets, which is also the
   privacy-correct behaviour: the monitor should not resolve executable paths for
   unrelated processes.
2. **A sample was being re-taken needlessly.** Enabling a boundary already takes a
   real measurement, so a self-test immediately afterwards enumerated the whole
   host again for the same instant. A sample younger than 2 s is now reused.
3. **The first two fixes cost information.** The reuse path initially reported a
   violation *count* with no descriptions. The live observation summary now carries
   the descriptions, so the self-test still says what was seen, not just how many.

Preflight went from timing out at 25 s under suite load to **~5.6 s idle**,
verified across three consecutive runs. This was caught only because the two
preflight tests exercise real host I/O — the mocked suites could not have shown it.

### Evidence hygiene

Preflight's boundary persists no trace: each `preflight` call was leaving a trace
in `.maos/network-evidence/`, which had reached 29 files after one afternoon of
testing and would grow without bound for a user who checks the boundary daily.
Self-test teardown now discards its scratch trace (`discardEvidence`), while a
boundary established for real work keeps its trace. Verified: two consecutive
preflight runs leave the trace count at 32, while `run --enforce-firewall` takes
it from 32 to 33.

Boundary lifecycle audit events carry a `selfTest` flag so a reader of the chain
can distinguish a preflight probe from a boundary that guarded real work:

```
seq 1499 PROCESS_BOUNDARY_ENABLED  selfTest=true    # preflight probe
seq 1503 PROCESS_BOUNDARY_DISABLED selfTest=true
seq 1508 PROCESS_BOUNDARY_ENABLED  selfTest=false   # judged run
seq 1520 PROCESS_BOUNDARY_DISABLED selfTest=false
```

## Residual risks (open, not hidden)

1. **Host scope remains unhardened.** The F9-03 machine-wide path still applies
   the broad synthesized plan, and its previously identified defects are unfixed:
   verification matches rule *names* only (a disabled or action-flipped rule would
   still verify), and the "pre-change snapshot" captures only `MAOS_*` rules and is
   empty by construction. Host scope should be treated as unavailable for
   production until addressed. It is no longer on any default path.
2. **Whether Windows Firewall filters loopback traffic was not empirically
   confirmed on the target host.** This is the fact the host plan's design rested
   on, and it is now moot for the default path. It still needs confirmation before
   host scope could ever be used, and the safe check is `New-NetFirewallRule
   -WhatIf` in an elevated shell — not a live block-all.
3. **`WindowsFirewallAdapter.isElevated()` relies on `net session`**, which
   depends on the `LanmanServer` service running, not solely on elevation. Not on
   any default path; relevant only if host scope is revisited.
4. **Process scope is observational, not preventive.** It observes and reports
   attributed traffic; it does not prevent a socket from being opened. Prevention
   remains the endpoint allowlist and service identity pinning.
5. **Attribution is best-effort.** An externally launched model server is outside
   the boundary unless passed via `--monitor-pid`.
