## How this was found

While verifying F9-10, the chain in this repository was corrupted twice, and the
judged-run suite failed with:

```
SERVICES_INIT_FAILED: CORRUPT_AUDIT_LOG: AUDIT_HEAD_COUNT_MISMATCH: expected 861, found 862
```

Investigation showed two records sharing a sequence number, written 1–3 ms apart
from different sources (`approval` / `conflict_review`, `office-input-service` /
`network-monitor`). Both historical chain files
(`audit-chain-history.jsonl`, 1877 records; `audit-chain-archive.jsonl`, 1818
records) are perfectly linear, which established that forking is **not** a normal
product condition — it requires concurrent writers.

Combined with the fact that `maos industrial start`, `maos industrial preflight`,
and the dashboard run as separate processes against one project root, this is a
reachable condition in the documented operating mode, not a test artifact.

---

## Root cause

`AuditService.recordAuditEvent` is a read-modify-write with no inter-process lock:

| Step | Operation | Hazard |
| --- | --- | --- |
| 5 | `readAllRecords()` → `sequence = records.length` | reads a stale count |
| 6 | `engineChainAppend(...)` — **spawns the Rust engine** | multi-millisecond window |
| 8 | `openSync('a')` + write + fsync, then `writeAuditHead` | both writers commit |

Within a single process the function is synchronous and therefore atomic. Across
processes it is not. Two writers interleaving between steps 5 and 8 both derive
the same `sequence` and both link `previous_hash` to the same predecessor, forking
the chain. The head then records whichever writer committed last, so
`recordCount` and the log length disagree — and because step 5 validates the head
before every append, **every subsequent append throws `CORRUPT_AUDIT_LOG`**. The
chain can no longer be extended or verified.

The window cannot be closed by in-process atomicity; it must be closed across
processes.

---

## Fix

`AuditService` now performs steps 5–8 inside a cross-process append lock
(`.maos/audit/audit-chain.lock`):

- **Acquisition is atomic** — `fs.writeFileSync(..., { flag: 'wx' })`, the same
  primitive the existing lifecycle lock uses.
- **Fail-closed** — if the lock cannot be taken within the budget (default 5 s),
  the append is **refused** with `AUDIT_LOCK_TIMEOUT` rather than proceeding
  unlocked. A refused append is recoverable; a forked chain is not.
- **Abandoned locks are reclaimed** — a lock whose owner PID is dead is stolen
  immediately. Unlike the long-running lifecycle lock, an audit lock has no
  legitimate reason to outlive its owner, so no age threshold is required.
  Unreadable lock files are also reclaimed.
- **Always released** — a `finally` releases the lock whether the append succeeds
  or throws, so it is never held across appends.
- **Always terminates** — the deadline is re-checked at the top of every
  acquisition attempt, *including* the abandoned-lock reclaim path. If removing a
  stale lock keeps failing (for example the file is open without delete-sharing on
  Windows), acquisition still gives up with `AUDIT_LOCK_TIMEOUT` rather than
  spinning. A hang inside an audit write would stall the whole CLI, so this path
  is bounded explicitly rather than assumed to terminate.

---

## Verified properties

1. **Serialisation** — sequential appends produce a linear chain
   (`sequence == index`, no link breaks) with a head matching the last record.
2. **Fail-closed** — an append attempted while a live-PID lock is held throws
   `AUDIT_LOCK_TIMEOUT`, and the chain is left untouched and un-forked.
3. **Honest refusal** — the error names the reason and explicitly states that
   appending unlocked would fork the chain.
4. **Recovery** — locks with a dead owner PID, and unreadable lock files, are
   reclaimed and the append succeeds.
5. **Hygiene** — the lock does not exist after a successful append, and does not
   exist after a *failed* append (the critical section releases on throw).
6. **Cross-process** — two real OS processes each appending 20 records
   concurrently produce exactly 40 records, `sequence == index` throughout, zero
   link breaks, a head of 40 matching the final record, and a chain the product's
   own Rust-engine verifier accepts.

## Repair performed on this repository

The live chain (`.maos/audit/audit-chain.jsonl`) had been forked by concurrent
MAOS processes. It was repaired by removing the duplicate sibling record that the
head did **not** commit to, leaving every surviving record's original hash intact
— no rehashing, and no head rewrite.

- Backup: `.maos/audit/audit-chain.jsonl.pre-f910-repair.20260927131711.bak`
- Result: 861 records, `sequence == index` throughout, zero link breaks, head
  consistent, `maos industrial verify audit` reports **Chain Integrity: VERIFIED**

The removed records were events written by test/CLI processes during this work,
not operator evidence.

## Residual risks

1. **The lock protects appends, not rotations.** The archive/history rollover
   paths were not audited for concurrent-writer safety.
2. **A writer that dies holding the lock is only reclaimed by the next writer**,
   which will steal it on the dead-PID check. There is no background reaper.
3. **`AUDIT_LOCK_TIMEOUT` surfaces as a hard failure of the calling operation.**
   Under sustained multi-process load a caller may need its own retry; 5 s is
   well above the observed append cost.
4. **This is a lock, not a transaction.** Two processes appending concurrently are
   serialised, but nothing prevents a second process from rewriting the file
   wholesale; that remains detectable only by `verifyChain()`.
